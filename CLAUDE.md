## What this repo is

A template for building **sub-20-millisecond audiovisual Sidecartridge Multi-device microfirmware apps** for the Atari ST / STE / MegaST(E) — games, demos, and console/computer emulations where the speed of putting a colourful 320×200 screen up matters. Each "app" is a UF2 image that runs on a Raspberry Pi Pico (RP2040) plugged into the Multi-device cartridge slot, emulating a ROM cartridge for the Atari, while also handling SD card I/O and per-app config. You draw into a **320×200, 16-colour framebuffer** in the Pico's RAM and the firmware blits it to the ST screen every VBL (50 Hz) for you; keyboard input and YM audio come for free. The primary extension point is "draw into the framebuffer, the m68k blits it for you". Public build/usage docs are at <https://docs.sidecartridge.com/sidecartridge-multidevice/programming/>.

**You develop 100% on the RP2040 side — the framework does the heavy lifting:**
- **Dual (page-flipped) framebuffer on the Atari ST side** — tear-free display, fully managed for you.
- **Real 50 Hz**, locked to the ST's vertical blank.
- **~19 ms of compute every VBL** for your app to draw its frame.
- **Chunked drawing on the RP2040** — you write one byte per pixel; the framework does the chunked → Atari ST planar conversion for you.
- **~1 ms per VBL** for that chunky→planar conversion (split across both cores).
- **Sampled sound**: 8-bit at 12.5 kHz through the DMA sound chip on an STE or a Mega STE, ~6 kHz 6-bit out the YM2149 elsewhere; one asset plays on both. Or, in the **25 fps profile**, 25 kHz and ~22 kHz (see "Profiles" below).
- **Atari ST keyboard, mouse and joysticks handled on the RP2040** — decoded scancodes, mouse movement and stick states delivered straight to your app.

Network plumbing (WiFi / lwIP / mbedTLS / httpc) was deliberately stripped — apps that need it bring it back from `md-microfirmware-template` upstream.

## Build

Top-level build is driven by `build.sh` in the repo root:

```bash
# <board_type> = pico_w
# <build_type> = debug | release   (both compiled as CMake Release, -O3 — see below)
# <app_uuid_key> = UUID4 identifying this app, must match desc/app.json
./build.sh pico_w release 44444444-4444-4444-8444-444444444444
```

Use the dev UUID `44444444-4444-4444-8444-444444444444` for local builds — any other UUID keys the UF2 to an identity with no config sector and the app jumps to Booster.

To rebuild only the m68k side (needed whenever `target/atarist/` changes, since it regenerates `rp/src/include/target_firmware.h`), run `target/atarist/build.sh` directly.

Required host environment:
- ARM GNU Toolchain 14.2 — export `PICO_TOOLCHAIN_PATH` to its `arm-none-eabi/bin` dir.
- `atarist-toolkit-docker` (`stcmd`) — needed for the m68k target. `stcmd` requires a PTY (`pty=true`).
- SDK paths (auto-set from the repo if unset): `PICO_SDK_PATH`, `PICO_EXTRAS_PATH`, `FATFS_SDK_PATH`.

Build flow (orchestrated by `build.sh`):
1. Copies `version.txt` into `rp/` and `target/atarist/`.
2. Builds the Atari ST target (`target/atarist/build.sh`) via `stcmd make`. The cart→ST screen copy is the `FBDRV_INLINE` macro inside `userfw.s` (there is no separate `fbdrv.s` any more). Enforces a **16 KB hard limit** on `BOOT.BIN` (the cartridge code budget — `CART_CARTRIDGE_CODE_SIZE` in `rp/src/include/cart_shared.h`, mirrored as `CARTRIDGE_CODE_SIZE` in `target/atarist/src/main.s`); a build that exceeds it aborts with `ERROR: cartridge code is N bytes; limit is 16384`. A separate copy (`FIRMWARE.IMG`) is then padded to 64 KB to fill the entire shared region, and `firmware.py` converts it into `rp/src/include/target_firmware.h` (a C byte array embedded in the RP firmware, emitted 4-byte aligned). The script stops at the first failed step: it deletes the old header before `firmware.py` runs and exits 6 if none is produced, so a failed m68k build never leaves a stale `target_firmware.h` behind. At boot, `COPY_FIRMWARE_TO_RAM` (`memfunc.h`, length in 16-bit words) clears the whole 64 KB window, then copies the image by DMA through the XIP stream, which moves 32-bit words: an odd trailing word is copied on its own, and an array that is not 4-byte aligned is copied word by word. Debug builds check the window against the array after the copy.
3. Builds the RP firmware (`rp/build.sh`): pins submodule versions (pico-sdk 2.2.0, pico-extras sdk-2.2.0, fatfs-sdk v3.6.2, which releases its locks when a read fails, so a pulled card fails at once instead of hanging), runs CMake, produces `rp/dist/rp-<board>.uf2`. The FatFs configuration lives at `rp/src/ff/ffconf.h` and shadows the submodule's default via `target_include_directories(... BEFORE PRIVATE)` in `rp/src/CMakeLists.txt`, so the `fatfs-sdk` submodule stays pristine.
4. Computes MD5, renames to `dist/<APP_UUID>-<VERSION>.uf2`, and substitutes UUID/MD5/version into `dist/<APP_UUID>.json` from the `desc/app.json` template.

### Build gotchas
- **Both build types are CMake `Release` (-O3).** `rp/build.sh` maps `(board, build_type)` to a preset in `rp/src/CMakePresets.json` (`<board>-debug` / `<board>-release`); both presets set Release, and `<build_type>` sets only `DEBUG_MODE` (DPRINTF and the UART console on the RP, `_DEBUG` in the m68k assembly) and the dist filename, so a debug build runs the same optimised code as a release build. Up to v1.0.0beta every build was `MinSizeRel`, because a full Release build had once broken at runtime (no reproducer was recorded). `RP_CMAKE_BUILD_TYPE` overrides the CMake type in `rp/build.sh`, with a warning: `MinSizeRel` to compare against the old builds, `Debug` (-Og, asserts on) to step through the code in a debugger; the build ID carries it (`+minsizerel`, `+cmakedebug`). Release takes about 27 KB more flash than MinSizeRel; the heap keeps the same room in a release build and 4 KB less in a debug build (the ROM3 ring's alignment padding). The hot compute files keep their `#pragma GCC optimize("O3")`, so they stay fast in a MinSizeRel build too.
- **`APP_PROFILE=PROFILE_25FPS`** in the environment (`APP_PROFILE=PROFILE_25FPS ./build.sh pico_w release <uuid>`) builds the 25 fps profile (`rp/src/include/profile.h`; see "Profiles"). `rp/src/CMakeLists.txt` passes it on as a define; the build ID ends in `+25fps` and `tools/dev/flash.sh` builds it in its own folder. The ST image is the same for both profiles.
- `RELEASE_DATE="YYYY-MM-DD HH:MM:SS"` fixes the date the images carry (the RP's debug banner, the SDK's binary-info build date and the cartridge header's GEMDOS date and time), so two builds of one commit are byte-identical. Unset, `build.sh` takes the time of the build, once for both images. `<build_type>` is `release` or `debug` in any case, anything else stops the build, and it sets `DEBUG_MODE` for both targets (the m68k code is assembled with `_DEBUG` from it).
- **The cartridge must be live before TOS looks for it.** On a power-on the ST checks the cartridge about 0.4 s after the RP starts. Anything slow before `emul_start()` copies the image (a chatty debug trace, a slow flash or SD operation) can make the ST boot to GEM without the app. At 115,200 baud the debug trace alone delayed the image by about 0.3 s; at 921,600 the image is ready about 45 ms after the first trace line.
- Harmless VASM warnings during the m68k build (`target data type overflow`, `trailing garbage after option -D`) can be ignored.
- VASM/`stcmd` errors like `the input device is not a TTY` mean `stcmd` was invoked without a PTY. `target/atarist/build.sh` already exports `STCMD_NO_TTY=1` for every `stcmd` call it makes; you only need to export it yourself if invoking `stcmd` directly from a non-TTY context (CI, sub-shells, build wrappers). Without it `stcmd make` fails; `build.sh` and `target/atarist/build.sh` then stop (`set -Eeo pipefail`) instead of going on with the previous `BOOT.BIN`, which used to give a working RP firmware that displayed garbage on the ST because `target_firmware.h` was stale.

### CI / release
- `.github/workflows/build.yml` builds `pico_w` release and debug on every PR, with the toolchain local builds use (ARM GNU Toolchain 14.2.rel1, downloaded from ARM and cached; Ubuntu's `gcc-arm-none-eabi` is another compiler and gives another image) and atarist-toolkit-docker v1.3.0 with `STCMD_NO_TTY=1`. The build is dated by its commit (`RELEASE_DATE`), so it matches a local build of that commit with the same date byte for byte. A job summary gives the build ID, the ELF's size and the UF2's MD5.
- `.github/workflows/release.yml` triggers on `v*` tags: builds with the same toolchain, toolkit and date, attaches UF2 + JSON to the GitHub Release, uploads to `s3://atarist.sidecartridge.com/` (skipped when the app UUID is the dev UUID).
- `make tag` tags HEAD with the contents of `version.txt` and pushes the tag (which triggers release).
- `upload_s3.sh <file>` is a manual one-off uploader; needs `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`.

### Tests
**Host tests** (`tests/host/`: `make -C tests/host test`, a second or two; CI runs them before the firmware build, and a failure fails the pull request) cover the pure logic. `test_fb_blit.c`: the blits' clipping at every edge, against a pixel-by-pixel reference. `test_chunk_layout.c`: what the app draws is what the ST shows, through the RP's transpose and chunk-reversed publish and a model of the m68k's MOVEM blit and of the blitter's copy, in one run and in pieces. `test_layout.py`: the ST's and the RP's copies of every shared constant agree (the window, the command values, the ROM3 windows, the blit's shape, the audio rate). `test_wav_to_ym4.py`: the sample converter and the `.YMS` files the RP's reader accepts. `test_png_to_bitmap.py`: the indexed-PNG converter (every PNG filter at every bit depth, the palette as ST words, the key colour, tiles in order, the images it refuses, and a header that compiles and gives back every pixel). `test_audio.c`: the audio slices against a simulated ST. `test_audio_dma.c`: the DMA sound output against a simulated STE (steady play, stalls, a missed VBL, an ST reset, YM data and PCM on both outputs), built and run for both profiles (`PROFILE_TESTS` in the Makefile). `test_ikbd_demux.c`: the IKBD decoder, every packet and loss rule, then a simulated IKBD and ST with bytes lost, dropped and read twice (reported losses never turn packet data into key presses; every kind comes back in step). The C tests build firmware units unchanged with the host compiler, under the address and undefined-behaviour sanitizers; `shim/` stands in for the few SDK headers they include (core 1 is a thread). To add one: a `tests/host/test_*.c` whose first line names the firmware sources it compiles (`// units: rp/src/fb_blit.c`), with `test.h`'s `CHECK` / `CHECK_EQ` / `TEST_END`, or a `test_*.py` unittest module. A new constant both sides share gets a row in `test_layout.py`'s `PAIRS`. Everything that needs the SDK, the bus or timing is verified on hardware: the build succeeds, the UF2 boots, and the app behaves on the ST.

**With the Debug Probe attached** (SWD and the debug UART), `tools/dev/` does most of that from the host; `tools/dev/README.md` has the details. `flash.sh <debug|release>` builds out of tree, flashes and checks over SWD that the RP runs that build. `console.py watch` captures the debug console (921,600 baud; release builds have none) into `tools/dev/logs/console.log`. `swd.py` reads the running RP without its help: `stopwatch` (debug builds with `TIME_STUDY = 1` in `userfw.s`: the ST's own timeline, see "The ST's budget"), `counters` (frames published, blits acknowledged, IKBD bytes and packets, the decoder's resyncs and count mismatches, the IKBD's restarts, ACIA and ring overruns, audio slices; per second with `--watch`), `ikbd-log` (debug builds: every sample the IKBD decoder sees, recorded in order, with its own check of the ST's byte counts), `heap`, `shared`, `fb` (the framebuffer as the ST shows it, as a PNG), `crash`, `postmortem`, `select`, `reset`. In debug builds `key` and `app` drive the app through the devhooks mailbox (`rp/src/include/devhooks.h`): keystrokes as from the ST, and the demo dispatcher's `demo N`, `menu`, `overlay`, `slow_frame`, `input_mode N`, `ikbd_cmd BYTE...`, `audio_out 0|1` (the DMA chip where there is one / the YM, from the next ST boot), `tone HZ` (a sine through the PCM path; 0: `DEMO.YMS`), `copy_mode 0-2 [PIECE]` (who copies the frame on the ST: auto, the CPU, the blitter). `tools_harness.py --build --flash --reset` checks all of it against the device. Flashing stops the cartridge bus, so reset the ST afterwards; never use OpenOCD's own `reset` or `program` (core 1 is the c2p worker and must start with core 0).

## Architecture

The firmware is a **two-target build**: m68k assembly that runs on the Atari ST is compiled into a ROM image, embedded as a C array inside the RP2040 firmware, and served back to the Atari over the cartridge bus that the RP2040 emulates via PIO + DMA.

### Framebuffer pipeline (the headline feature)

End-to-end, every visible pixel on the ST goes through this path each VBL:

1. **RP draws into a chunked off-screen buffer** at RP `0x20000000+` (`fb_chunked_buffer`, 320×200 bytes = 64 KB, one byte per pixel, palette index in low nibble). `fb_font.c` writes text; `fb_blit.c` writes rectangles / bitmaps / sprites with color-key.
2. **RP publishes via chunky-to-planar conversion**. The chunked buffer is bit-transposed to ST planar 4 bpp by a hand-written Thumb assembly worker (`fb_chunked_asm.S` — `fb_c2p_half`). For each 4-pixel uint32 group, plane K's 4-bit nibble = `((q >> K) & 0x01010101) * 0x80402010 >> 28`. Work is split between **Core 0 (top 100 rows) and Core 1 (bottom 100 rows)**, synced via the inter-core FIFO. Both cores write into a 32 KB RP-RAM scratch (`fb_planar_scratch`) in natural row-major order; `fb_chunky_to_planar` then publishes the result into the cart FB at `$FA8300` (RP `0x20030000 + 0x8300`) with the 48-byte m68k MOVEM chunks **pre-reversed** (so the m68k's predec store in step 3 lands each chunk at its natural image position — see "Framebuffer chunk layout for the m68k MOVEM blit" in `cart_shared.h`). Total conversion time: ~1 ms c2p + ~60-120 µs chunk-reversed memcpy.
3. **m68k blits cart FB → ST screen page** inside `userfw.s`'s VBL loop via the `FBDRV_INLINE` macro — a fully unrolled `movem.l (a6)+, d0-d7/a1-a4` load + `movem.l d0-d7/a1-a4, -(a5)` predec store (**12 longwords / 48 bytes per iter, 666 iterations** for the full 200-line low-res FB, plus a `d16(a5)` MOVEM tail copying the last 32 bytes). A0 and A7 are intentionally omitted from the MOVEM list: A0 is the dedicated Timer-B audio cursor (kept stable across the macro so the audio IRQ handler doesn't have to save/restore it), and A7 keeps the supervisor SP valid so IRQs can fire safely during the macro. Predec mode is 4 cyc/iter faster than `d16(a5)` (8+8n vs 12+8n on 68000), at the cost of writing each chunk in reverse memory order — which is exactly what the RP-side chunk-reversed cart FB layout from step 2 compensates for. A5 is initialised to `UFW_SCREEN_PAGE + 31968` (page end of chunked region) and decrements back to page start over the 666 iters. The same code runs on plain ST / STE / MegaSTE / TT / Falcon; on an STE or a Mega STE the blitter copies instead (see "The blitter" below).
4. **m68k flips video base** to the page it just wrote, toggling `UFW_SCREEN_PAGE` between `$70000` and `$78000` (`UFW_SCREEN_XOR`), so the display always reads from a stable page while the next blit fills the other.
5. **Blit and publish never overlap.** The m68k blits only when the low word of the RP's frame counter (`FB_FRAME_COUNTER_ADDR`, bumped as the last write of every `fb_publish()`) has changed since its last blit (`UFW_LAST_FRAME`), and only then flips and acknowledges (`$FB8400`). `fb_publish()` waits for that acknowledgement before it overwrites the cart FB, and after it the m68k reads nothing until the counter changes again. So a publish can happen at any moment, and an app slower than a frame drops frames instead of tearing. The counter is read with one `move.w`: a longword arrives as two bus reads with its halves swapped.
6. **PALETTE_IDX0 (`$FFFF8240`) doubles as a timing tape-measure** — `userfw.s` writes it at three points (post-vsync, blit-start, blit-end) so the ST border shows the blit cost as colored bands. White band = `FBDRV_INLINE` in flight (~17 ms at FB_COPY_LINES=200). Green band = slack until next vsync.

The number of lines copied by `FBDRV_INLINE` is parameterized by `FB_COPY_LINES` (default 200). Leaving rows untouched lets an app keep a static status bar in the destination ST page that the FB blit never overwrites. `FBDRV_TOTAL_BYTES = FB_COPY_LINES * FB_ROW_BYTES` is divided by `FBDRV_ITER_BYTES = 48` to derive `FBDRV_MAIN_ITERS`; trailing bytes (at most 47) are picked up by a small `d16(a5)` MOVEM tail block emitted via `ifne FBDRV_TAIL_BYTES`. The tail's MOVEM register list must hold exactly `FBDRV_TAIL_BYTES / 4` longwords — at FB_COPY_LINES=200 the tail is 32 B (`d0-d7`); at 199 it's 16 B (`d0-d3`); at 198 it's 0 B (block skipped). Adjust the register list manually when changing FB_COPY_LINES.

**The ST's budget.** In the 50 fps profile the full-screen blit and the audio leave the ST about 0.27 ms of each VBL on a Mega ST (sometimes 0.07 ms). The instrument is the ST's stopwatch, `TIME_STUDY = 1` in `userfw.s` (0 by default, about 40 µs a VBL): MFP Timer-A runs free at /10 (4.07 µs a tick), an interrupt counts its wraps (about 1% of the CPU), and the VBL and four points of the loop (the wake, the copy's start and end, the loop's end) report its low 16 bits at `$FB8Bxx` (the point), `$FB8Cxx` / `$FB8Fxx` (the ticks), so every duration is a difference on one timeline, even across a VBL. Debug builds of the RP keep the points (`fbStopwatch`, read by `tools/dev/swd.py stopwatch`) and the slack of each copy before the VBL that may start the next frame (`fbSlackHist`, `fbSlackMinUs`, `fbSlackLate` in `fb.c`). Measured with it on a Mega ST: the full MOVEM copy takes 17.65 ms (666 × 212 cycles, as the tables say; the cartridge adds no wait states), a Timer-B sample about 152 cycles (2.1 ms a VBL at 5,585 Hz, more than the 112 of the tables: the MFP's acknowledge and the YM's accesses). Anything more the ST does per VBL comes out of that slack: every IKBD byte is an interrupt of 30–40 µs, so while the mouse moves fast (up to 9 bytes a VBL at the mouse modes' threshold of 4, 16 at threshold 1) some blits end after the next VBL and that frame waits one: 50 frames a second at rest, 30–40 with the mouse moved flat out; the sound stays clean. That is accepted; an app that needs a steady 50 fps with the mouse blits fewer lines (about 88 µs per line). On an STE or a Mega STE the sound goes through the DMA chip, Timer-B stays off and its 2.1 ms per VBL are free: measured on a Mega STE, the mouse moved flat out left the frame rate at 50 (30–38 on the same machine forced to the YM). In the 25 fps profile a frame has two VBLs: see "Profiles".

**Profiles.** The app chooses at compile time (`APP_PROFILE`, `rp/src/include/profile.h`) between two trades of frames for sound:

| | `PROFILE_50FPS` (default) | `PROFILE_25FPS` |
|---|---|---|
| Frames | every VBL, 50 fps | every second VBL, 25 fps on every machine |
| YM (plain ST, Mega ST) | 5,585 Hz (Timer-B count 110) | 21,943 Hz (count 28) |
| DMA chip (STE, Mega STE) | 12,517 Hz | 25,033 Hz |
| Suits | arcade games, full-screen effects | story games with rich sound (laserdisc-style) |

The ST image is the same for both: `fb_init()` writes the profile at `PROFILE_ADDR` / `CART_PROFILE_OFFSET` (shared slot 8) and `userfw` reads it once at boot, for Timer-B's count, the DMA mode and lead, and the VBLs a frame (`UFW_VBLS_A_FRAME`: it takes a new frame no sooner than that many VBLs after the last one, counted by `userfw_vbl` in `UFW_VBL_COUNT`; a frame late by a VBL delays only the next). The constants of both are in `cart_shared.h` (`CART_PROFILE_*`) and `inc/sidecart_layout.s` (`PROFILE_*`), checked by `test_layout.py`. YM sources (`.YMS` files, the built-in jingle) stay at 5,585 Hz (`AUDIO_YM_SOURCE_RATE_HZ`) and are resampled to the output's rate. Measured on a Mega ST at 25 fps: the full copy with 22 kHz sound interrupting it takes 29.9 ms and ends 10.1 ms into the frame's second VBL, 9.75 ms before the next frame (8.9 ms with the mouse moved flat out, 1,429 packets, no IKBD error); that is about 5.5 ms of free CPU, Timer-B taking 43% of the rest. The sound was clean on both machines. Apps that step their state once a frame move half as fast at 25 fps: scale by `PROFILE_VBLS_A_FRAME`, or use time (`time_us_32()`), as Zap does for its round.

**The blitter.** At boot `userfw` asks TOS for a blitter (XBIOS `Blitmode(-1)`, bit 1: an STE, a Mega STE, a Mega ST fitted with one) and reports it after the hello at `$FB8Exx` (`st_session_features()`, `stSessionFeatures` over SWD). The blitter copies the frame exactly where `FBDRV_INLINE` would: a chunk of 48 bytes per line going forward in the cart FB, the destination going back a chunk per line (Y increment −94) from the page's last chunk, then the tail. It copies in hog mode, 40 chunks at a time (about 1 ms; an IKBD byte must be read within 1.28 ms), and the interrupts run between pieces. Both copies are bound by the bus (8 cycles a word against MOVEM's 9), so the blitter saves only about 1.4 ms of a full screen, and it holds the CPU off: Timer-B's samples come late. Measured on a Mega STE (8 MHz, DMA sound): the slack after the blit went from 1.9 ms to 3.3 ms, the tone sounded the same, and with the mouse moved flat out it stayed at 50 fps with no IKBD overrun or resync. Measured on a Mega ST with a 440 Hz tone: the slack went from 0.25 ms to 3.4 ms in 40-chunk pieces (part of it dropped Timer-B interrupts; the sound breaks), 1.0 ms in 7-chunk pieces and 0.4 ms in 4-chunk pieces, and even those made the tone audibly rougher; sharing the bus instead of owning it took longer than a VBL (25 fps). So the RP's word at `BLIT_MODE_ADDR` / `CART_BLIT_MODE_OFFSET` (slot 7, read every VBL; `fb_set_copy_mode()`) defaults to auto: the blitter when the sound goes through the DMA chip (Timer-B off), the CPU on the YM path. `CART_BLIT_MODE_BLITTER` takes the blitter on any path (a silent app on a Mega ST: 3 ms more), `CART_BLIT_MODE_CPU` the 68000; the high byte sets the chunks per piece. Without a blitter the CPU copies whatever the mode. Leaving to GEM after the blitter copied leaves TOS's drawing intact (it sets every register it uses).

### IKBD pipeline (keyboard, mouse, joysticks + ESC exit)

`userfw.s` owns the Atari ST IKBD ACIA at `$FFFFFC00`/`02` end-to-end, replacing TOS's handlers; the RP decides what the IKBD reports and decodes everything it sends:

1. **m68k boot stubs 4 IRQ vectors** — HBL (`$68`), Timer-A (`$134`), Timer-C (`$114`) and Timer-D (`$110`) point at a 1-instruction `userfw_dummy_irq` (just `rte`). MFP Timer A/C/D are disabled+masked at IERA/IERB so they never fire; HBL is masked by SR=$2300 (IPL=3 blocks IPL≤3). The dummies are defense-in-depth. Timer-B (`$120`) is owned by the audio pipeline (see "Audio pipeline" below), running in /4 delay mode at TBDR=110 → ~5,585 Hz, and the keyboard ACIA (`$118`) by `userfw_acia_irq` (step 4).
2. **m68k boot resets the IKBD** — `$80 $01`, sent when the ACIA's transmitter is empty (`IKBD_SEND`), then it reads and drops everything up to the reset's answer (`$F0`/`$F1`) and waits a short settle delay: for a while after a reset the IKBD undoes a mouse-off command, and TOS resets it moments before the cartridge code runs. It sends no mode command itself; the RP's go out from the first VBLs (step 3). On the way out to GEM, `$14` (joystick events) then `$08` (relative mouse) give TOS back its own setup; `$14` also turns the mouse off, so the order matters.
3. **The RP owns the IKBD's commands** — a 16-byte block at `IKBD_OUT_ADDR` / `CART_IKBD_OUT_OFFSET` (`$FA4018`, shared slots 2..5): a generation word, a length word and up to 12 command bytes, two to a word, the first in the high byte. When the generation changes, `.vbl_loop` sends the bytes one per VBL, only when the ACIA can take one (never waiting; a 0 sends nothing that VBL), then reports the generation's low byte at `$FB87xx`. The RP sets bit 15 of the generation while it rewrites the block and the ST re-reads the generation before each byte, so it never mixes two strings. After every boot the ST sends the block again (its saved generation starts at -1). The input modes (`ikbd.c`, `ikbd_set_input_mode()`): keyboard only (`$12 $15`, the default), mouse (`$15 $08 $0B 4 4`), mouse + joystick 1 (`$14 $08 $0B 4 4 $16`), two joysticks (`$12 $14 $16`); the keyboard works in every mode, and port 0 is the mouse or joystick 0, never both. None uses `$1A` (disable joysticks): on a Mega ST's IKBD, after `$1A`, `$14` brought port 0 back but stick 1 stayed silent with the mouse on; `$15` (the sticks report only when asked) stops the events instead. `$16` asks for the sticks' state once, since events only report changes. `$0B 4 4` is the mouse threshold: a packet once the mouse has moved 4 counts, which halves the bytes of a mouse moved fast (see "The ST's budget" above). The RP sends the mode again after a hello and after the IKBD restarts (step 6); `ikbd_send_commands()` sends other commands.
4. **m68k reads the keyboard ACIA from its receive interrupt** (`userfw_acia_irq`, MFP GPIP4, `$118`): one byte per interrupt, forwarded via a cart-bus read at `IKBD_WINDOW_BASE + byte` (`$FB8200..$FB82FF`) and counted. The 6850 holds one byte (a second one overruns it); reading it raises the ACIA's IRQ line and the next byte lowers it again, an edge the MFP sees, so there is no drain loop. The earlier poll inside `FBDRV_INLINE` left gaps longer than a byte time (1.28 ms) and a second byte overran the first. The handler saves D0/A1 (it can fire between a MOVEM load and its store in the blit) and never touches A0; with the MFP in auto-EOI mode there is no in-service bit to clear. When the ACIA flags an overrun the handler also reads `$FB8500`, which the RP counts (`ikbd_overruns()`). `userfw_vbl` reports the count's low byte every VBL at `$FB83xx`. The MIDI ACIA shares GPIP4, so its receive interrupt is off while `userfw` runs (`$15`) and TOS's `$95` is written back on exit.
5. **RP captures via commemul** — the 4 KB ROM3 DMA ring (`commemul.{c,pio}`, `COMM_RING_BITS`) records every read in `$FB0000`–`$FBFFFF`. `ikbd_consume_rom3_sample()` (the ring's callback, through `fb.c`) keeps the IKBD samples — bytes, the ST's counts, overruns, command reports, hellos — in order in a 256-entry ring that `ikbd_pump()` drains.
6. **RP decoder** (`ikbd_demux.c`, plain C, host-tested): `$00..$7F` a key press, `$80..$F5` a release, `$F6..$FF` a packet header with a fixed payload (`$F8`-`$FB` mouse dx dy, `$FE`/`$FF` a stick event, `$FD` both sticks, `$F6`/`$F7`/`$FC` never asked for). Keys go into a 16-entry event ring (`ikbd_pop_key()`); the mouse (movement since the last read, buttons, "pressed" latches: `ikbd_read_mouse()`) and the sticks (`ikbd_read_joystick()`) are state. A lost byte shifts every packet after it and turns packet bytes into keys, so the decoder watches for losses — an overrun report, a full ring, the ST's count not matching the bytes that arrived, a packet open at its second VBL, an invalid joystick byte, a packet never asked for — and then holds back key presses, mouse and joystick data until a VBL in which the ST read no byte, where the stream is certainly back in step; releases always pass, so no key stays down. `$F0`/`$F1` with keypad 0/`.` not down is the IKBD powering up again (a keyboard plugged back in): the keys still down are released and the mode is sent again. In mouse + joystick 1 mode the IKBD reports stick 1's fire only as the right mouse button (the same wire): the decoder shows it as stick 1's fire, and stick 1's events keep it.
7. **ESC exit** — when the decoder delivers an ESC press (`$01`) followed by an ESC release within 200 ms, `ikbd.c` writes `CART_CMD_BOOT_GEM` to the sentinel slot at `__rom_in_ram_start__ + CART_CMD_SENTINEL_OFFSET` via `cart_asM68kLong()` (cart-bus longword byte-swap). The m68k VBL loop polls the sentinel each frame and exits cleanly back to GEM on match.

Measured on a Mega ST with the input test (menu entry 5) and `tools/dev/swd.py ikbd-log`: every mode, switching between them, ESC to GEM from the joystick and the mouse modes (the GEM pointer works), a keyboard unplugged and plugged back, the mouse moved flat out for minutes: no overrun, resync or count mismatch.

The earlier ROM4 + DMA-IRQ-per-read capture route (a first attempt) saturated the Cortex-M0+ during fbdrv blits (~8M cart reads/sec) and silently dropped IKBD bytes; switching to the dedicated commemul DMA ring eliminated the loss.

### Audio pipeline (the STE's DMA chip, or the YM2149)

Two outputs, one per machine. On an STE or a Mega STE the **DMA sound chip** plays 8-bit samples at 12,517 Hz (25,033 in the 25 fps profile), no interrupt per sample; elsewhere **Timer-B** plays YM volume pairs at 5,585 Hz (21,943). The rates are the profile's (see "Profiles"). Both sides apply one rule: `userfw` takes the DMA path at boot when the machine's family (the hello byte, from `_MCH`) is the STE's and the RP has not asked for the YM (`AUDIO_OUT_ADDR` / `CART_AUDIO_OUT_OFFSET`, slot 6: `audio_prefer_ym()`); `audio.c` makes the same choice at each hello (`select_output`, `audioOutput` over SWD: 1 YM, 2 DMA). The app's sound is YM pairs (a loop, a `.YMS` file, a callback) or signed 8-bit PCM at any rate (`audio_play_pcm_loop()`, `audio_set_pcm_callback()`), and either plays on both outputs: the RP converts at runtime through the same 64-entry table both ways (a pair outside it by the YM's volume curve) and resamples linearly. In every case the RP writes ahead of what the ST plays, from a timer interrupt, out of a FIFO the main loop tops up, so the sound never tears and never repeats, whatever the app's frame rate.

**The DMA path** (verified on a Mega STE, TOS 2.06; the same image plays through the YM on a Mega ST):
- The chip loops over a 4 KB ring in ST RAM, `UFW_DMA_RING` at `$6F000` (below screen page A, the second documented use of Atari RAM), mono at the profile's rate (mode $81 at 12,517 Hz, $82 at 25,033). At boot `userfw` clears it, sets the frame to the whole ring, sets the Microwire (LMC1992) as TOS does (master, left, right 0 dB, tone flat, the YM mixed in) and starts the chip; on the way out to GEM or on `CMD_RESET` it stops it. Timer-B is never started on this path.
- Every VBL, right after the wake, `userfw` reads where the chip plays (the frame counter's middle and low bytes, the middle one read again as it moves), reports it by 16 bytes (`AUDIO_DMA_POS_UNIT`) at `$FB8Dxx`, and copies the cart buffer, the ring's mirror, from where its last copy ended up to the profile's lead (`UFW_DMA_LEAD`: 768 or 1,536 bytes, 3 VBLs) ahead of the chip: a missed VBL still finds samples. About 0.35 ms at 12,517 Hz (0.7 at 25,033), against Timer-B's 2.1 ms at 5,585 Hz.
- `audio.c`'s writer keeps the mirror written `AUDIO_DMA_AHEAD` (the lead plus 5/8 of a VBL: 928 or 1,856 bytes) ahead of where the chip plays now (the last report, plus the samples played since: a missed VBL sends no report), never inside what the ST copies; byte i of the ring is byte i ^ 1 of the RP's buffer. A late write is counted in `audioLateSlices`, an empty FIFO holds the last sample (`audioUnderruns`). The FIFO holds five VBLs of samples in both profiles (it shares the YM FIFO's memory), so the main loop may still go 80 ms between top-ups; a sample plays at most about 175 ms after its source made it.

**The YM path:**

1. **Build-time PCM → YM conversion** (`tools/wav_to_ym4.py`). Source `.SAM` / `.WAV` is downsampled to the target rate and each 8-bit PCM byte is mapped through the **1988 Ghostbusters demo's 64-entry SAMPLE1 LUT** (default `--mode dual-ghost`): the top 6 bits of each PCM byte index a (chA, chB) pair, emitted as 2 bytes per sample. Output is `rp/src/include/audio_sample.h` — a C array embedded in the RP firmware. The Ghostbusters LUT cherry-picks 64 of the ~135 distinct acoustic sums achievable from the YM's log volume curve, giving ~6 effective bits of resolution vs the 4-bit ceiling of single-channel playback. Other modes available: `single-a` (1 byte/sample, ch A only, Ayumi log LUT), `best-pair` (exhaustive search over all 256 pairs), `nibble` (linear truncation), `raw-byte` (passthrough).
2. **m68k VBL handler moves to the next slice** (`userfw_vbl` in `userfw.s`). The buffer at `$FA4100` is `AUDIO_SLICES` (4) slices of `AUDIO_SLICE_BYTES` (256; a VBL plays 224). On every vsync the handler, with the interrupts masked (Timer-B at IPL 6 outranks it), advances `UFW_AUDIO_SLICE` (a word in the state area), points A0 at that slice and reports it with a ROM3 read at `$FB8600` + slice. A0 is the **dedicated Timer-B audio read cursor** — kept out of `FBDRV_INLINE`'s MOVEM list so the IRQ handler doesn't have to save/restore it; the VBL handler saves the D0 it uses (it interrupts the blit between a MOVEM load and its store). About 30 µs per VBL, with the IKBD byte count it reports first (see the IKBD pipeline).
3. **RP writes the slices ahead** (`rp/src/audio.c`). A repeating timer interrupt every 4 ms finds the ST's slice from the latest report in the ROM3 ring (`commemul_latest()`, read-only) and writes the two slices after it from a RAM FIFO — never the one playing. `audio_render_frame()`, called from the main loop, only tops that FIFO up with the app's fill callback (a loop in flash, a `.YMS` file on the SD card, the app's own generator), so FatFs stays out of the interrupt. The main loop may go `AUDIO_FIFO_SLICES` (4) VBLs = 80 ms between two top-ups without an underrun; a sample plays at most `AUDIO_FIFO_SLICES` + 2 VBLs = 120 ms after the callback made it. An empty FIFO holds the last sample (no click, never stale data). `audioSlicesWritten`, `audioLateSlices` and `audioUnderruns` are readable over SWD (`swd.py counters`). Measured on a Mega ST: 50.0 slices a second in every demo, with every frame 30 ms late, and with a 60 ms frame every second; no late slice, no underrun. Before this, the refill landed in the slice the ST was playing and a 20 ms time gate made the ST replay a stale slice about 4 times a second even at 50 fps.
4. **m68k Timer-B handler plays the pair** (`userfw_timerb_audio`). MFP Timer-B is in /4 delay mode with the profile's count: 110 → 5,585.45 Hz, ~112 fires per PAL VBL (28 → 21,942.86 Hz, ~438). Each fire: `move.b (a0)+, $FFFF8802.w` (vA → ch A vol, reg 8 latched on entry) → `move.b #9, $FFFF8800.w` (latch reg 9) → `move.b (a0)+, $FFFF8802.w` (vB → ch B vol) → `move.b #8, $FFFF8800.w` (re-latch reg 8 for next fire) → `rte`. ~68 cyc handler body + ~44 cyc IRQ entry/exit = ~112 cyc/fire by the tables; measured about 152 (the MFP's acknowledge and the YM's accesses): 2.1 ms a VBL at 5,585 Hz (~11%), 8.3 ms at 21,943 (~42%). MFP is in **auto-EOI mode** (VR S=0) so the in-service bit clears automatically per IACK cycle — no software EOI needed in the handler.
5. **YM boot state** — boot enables channels A + B in the mixer (`MIXER = $FC`, tones on, noise off, periods=0 for a DC pass-through), zeroes both volumes, then latches reg 8 so the first Timer-B fire writes ch A directly.

Tuning knobs:
- The profile sets the rates (`APP_PROFILE`, see "Profiles"). Each profile's Timer-B count, YM rate and bytes a VBL (224 or 878, within a slice of `AUDIO_SLICE_BYTES` = 1024), DMA mode, rate and lead are named constants on both sides (`CART_PROFILE_*` / `PROFILE_*`); the comment above `TIMERB_PRESCALER` in `userfw.s` states the whole chain, and `tests/host/test_layout.py` fails when the two sides disagree. A new rate means new constants there, and a slice or a ring that holds a VBL of it.
- `AUDIO_FIFO_SLICES` in `rp/src/audio.c` (4, or 3 at 25 fps where a VBL of samples is four times larger) trades latency for stall tolerance on the YM output: fewer slices, less delay, a shorter stall allowed. At 25 fps the main loop tops it up every 40 ms.
- The DMA path's ring (`AUDIO_DMA_RING_BYTES`, the audio buffer's 4 KB) and position unit (16 bytes: the report fits a byte) are shared constants (`test_layout.py`); `AUDIO_DMA_AHEAD` in `audio.c` stays the lead plus the writer's period and how late it sees a report.
- PCM assets: `tools/wav_to_ym4.py --mode pcm --target-rate 12517 --header-output x.h <source>` writes signed 8-bit samples for `audio_play_pcm_loop()`.
- YM-pair assets (`audio_sample.h`, `.YMS` files: `python tools/wav_to_ym4.py --target-rate 5585 --mode dual-ghost <source>`) are at `AUDIO_YM_SOURCE_RATE_HZ` (5,585 Hz) in both profiles: the RP resamples them to the output's rate.
- Audio uses one word of Atari RAM on the YM path, `UFW_AUDIO_SLICE` in `userfw`'s state area, and on the DMA path the 4 KB ring at `$6F000` and words at `$77F80` (the machine, the path, where the last copy ended, the profile's lead); the cart buffer at `$FA4100` is the entire I/O path, and the Timer-B handler keeps its state in A0.

### Atari ST side (`target/atarist/`)
- `src/main.s` — m68k cartridge header + boot dispatcher. Lives at `$FA0000` (ROM4 cartridge region). `pre_auto` (CA_INIT bit 27) runs in supervisor mode, copies `start_rom_code` below ST screen memory, jumps there, checks resolution (high-res falls to GEM with a warning), then **`jmp USERFW` directly** — no terminal command dispatch in the default path. The old `check_commands` / `rom_function` indirection is still defined (for apps that want CMD_START-style handoff from the RP) but unused.
- **No Atari RAM**, but for three documented exceptions: the two screen pages at `$70000`/`$78000` with `userfw`'s state area in the tail of page A (`$77F00`–`$77FFF`), and on STE-class machines the DMA sound ring just below them (`$6F000`–`$6FFFF`). Otherwise the cartridge code deliberately uses none of the ST's RAM (no `.bss`, no heap). Data lives in registers or the shared region. Adding naive BSS to `userfw.s` will silently corrupt system variables — keep state in `APP_FREE` / `SHARED_VARIABLES`, the cart code itself (which is **read-only** from m68k — writes bus-error), or registers. Key live registers across the `userfw.s` VBL loop: A0 = Timer-B audio read cursor (reset to `AUDIO_BUFFER_ADDR` by `userfw_vbl` each VBL, never in any MOVEM list), A5 = per-VBL FB destination scratch (predec target for `FBDRV_INLINE`), A6 = per-VBL FB source scratch (postinc reader of the cart FB), A7 = SP (also kept out of MOVEM so IRQs stay safe). D0-D7 / A1-A4 are scratch and are clobbered by the MOVEM macro.
- `src/userfw.s` — **the primary extension point for app-specific m68k code.** `src/userfw.ld` places `main.s` at offset `0x0000` (≤ 2 KB) and `userfw.s` at offset `0x0800` (`0x0800..0x3FFF`, 14 KB budget including the inline `FBDRV_INLINE` macro expansion). The previously-separate `fbdrv.s` module at offset `0x2000` was eliminated: the unrolled MOVEM block is now emitted inline at the userfw entry via the `FBDRV_INLINE` macro, so there's no jsr/rts overhead and no separate hand-written file to maintain. Total cart code ≤ 16 KB (`CARTRIDGE_CODE_SIZE`); current build is ~9.1 KB. `main.s` exposes the userfw entry as `USERFW equ (ROM4_ADDR + $800)`. The default `userfw.s` runs the FB blit + audio + IKBD VBL loop and exits on ESC; replace its body with your own per-frame logic, or extend it.
- **Every m68k module ends with a NOP tail**: `even`, eight `nop`s and a `<module>_end:` label, after its last code (after `include "inc/sidecart_functions.s"` in a module that includes it). `firmware.py` strips trailing zero bytes from the image, `pre_auto` relocates `start_rom_code..end_rom_code` in whole longwords, and the write sender and the 68000's prefetch read past the senders' wait loop: the last words of a module must be harmless to drop or to read past. `main.s` and `userfw.s` both end this way.
- Adding more m68k modules: add a new `.text_<name>` section in `userfw.ld`, mirror the offset with an `equ (ROM4_ADDR + $????)` in `inc/sidecart_layout.s`, and add the `.o` target to `target/atarist/Makefile`.
- Built via `stcmd make release` (m68k assembler in Docker). A 64 KB padded copy of the BOOT.BIN is then converted to `target_firmware.h` for inclusion in the RP build.

### Shared 64 KB cartridge region
The Atari ST sees a 64 KB window at `$FA0000`–`$FAFFFF` (mirrored RP-side at `0x20030000`). This is the **single source of truth** for any cross-target data layout — both sides derive every offset symbolically from constants in `rp/src/include/cart_shared.h` (RP-side) and `target/atarist/src/inc/sidecart_layout.s` (m68k side, included by `main.s` and `userfw.s`); `tests/host/test_layout.py` checks that the two agree. **Apps must never hard-code an address inside this region** — always reference the named offset/symbol.

### ROM3 signalling windows and ST sessions
The cartridge window is read-only from the ST, so the ST tells the RP things by *reading* ROM3 addresses (`$FB0000`–`$FBFFFF`), which the commemul ring captures: the high byte of the address says what the read means, the low byte carries a value. The windows are listed in `cart_shared.h` (`CART_ROM3_*`) and mirrored as equs in `inc/sidecart_layout.s`: `$FB82xx` an IKBD byte, `$FB83xx` the IKBD bytes read so far (low byte, every VBL), `$FB84xx` blit done, `$FB8500` the keyboard ACIA overran, `$FB86xx` the audio slice playing from this VBL, `$FB87xx` the IKBD commands of generation xx sent, `$FB88xx` the hello (xx = the machine), `$FB89xx` / `$FB8Axx` the TOS version's high and low byte, `$FB8Bxx` / `$FB8Cxx` / `$FB8Fxx` the stopwatch's point and ticks (`TIME_STUDY` only), `$FB8Dxx` where the DMA sound chip plays, by 16 bytes (every VBL, DMA path), `$FB8Exx` the ST's features (a blitter), after the hello. A new signal gets a window of its own.

What each side may assume about the other:
- **The ST and the RP reboot independently.** A power cycle restarts both; an ST reset restarts only the ST, and the RP keeps everything: the command sentinel, the app's state. An RP-only restart (a flash, SELECT) rebuilds the window while the ST keeps running.
- **The ST says hello at every boot.** `userfw` sends the TOS version and then the hello, from the `_MCH` cookie and the ROM header, before its setup. On the hello `st_session.c` writes `CMD_NOP` to the sentinel, well before the ST's VBL loop first reads it (the IKBD reset in between waits for the keyboard's answer). Without it an exit to GEM left `CMD_BOOT_GEM` in the sentinel and the next ST reset ran `userfw`, which left at once. The app sees the new session through `st_session_consume_boot()` (once per boot) and starts its own state over: `emul.c` sends the demo dispatcher back to its menu. `ikbd.c` sees the hello too and writes the input mode's commands again, since the ST reset the IKBD. `st_session_machine()` / `st_session_tos_version()` keep what the ST reported.
- **The sentinel is a level, not a queue.** The ST samples it once per frame; the RP writes `CMD_BOOT_GEM` to ask for the exit and clears it only on a hello.
- **The RP can refuse a boot.** `st_session_veto_boot(reason)` sets the boot status word: the ST, in `pre_auto`, prints the reason and returns to GEM instead of starting `userfw`. It reads the word once per boot (on a power-on about 0.3 s after the RP starts), and the veto holds until `st_session_allow_boot()`, so an ST reset retries once the cause is gone.
- **Return to Booster without a power cycle.** `st_session_return_to_booster()` saves `BOOT_FEATURE = BOOSTER` in the global settings, writes `CMD_RESET` to the sentinel and restarts the RP; `main()`'s `gconfig_init()` then jumps to Booster before anything runs, the only place `reset_jump_to_booster()` is safe. On `CMD_RESET` `userfw` masks interrupts (its handlers live in the cartridge, which stops answering once the RP restarts), copies a small stub to `UFW_RESET_STUB` (`$77F00`, the unused tail of screen page A) and runs it from there: a couple of seconds' wait, so TOS scans the cartridge once Booster serves it, then a cold reset through `$4`. The ST acts on it only while `userfw` runs; from GEM, reset it by hand. The demo menu does this on `B`.

### RP2040 side (`rp/src/`)
- `main.c` — only sets clock/voltage, calls `gconfig_init` (global config) then `aconfig_init` (per-app config), and hands off to `emul_start()`. If config init fails it jumps to the **Booster** app via `reset_jump_to_booster()` to bootstrap. **Don't add features to `main.c`** — put them in `emul.c` or a new module.
- `emul.c` / `emul.h` — the application's main loop and entry point. ~100 lines: erase + copy firmware to RAM, init IKBD ring, init romemul, init fb, init commemul, mount SD, configure SELECT, bring up the demo dispatcher (`demo_dispatcher_init()`), then loop `{fb_pump_rom3(); ikbd_pump(); drain key events → demo_dispatcher_handle_key(); demo_dispatcher_render_frame(); audio_render_frame();}`. `fb_pump_rom3()` (in `fb.c`) is the public wrapper that drains the ROM3 ring via `commemul_poll(fb_rom3_dispatch)` for IKBD demux + VBL frame-sync. The demo dispatcher (`demo_menu.c`) is the per-frame render driver; apps add foreground work inside that loop.
- `fb.c` / `fb.h` — **owns the 32 KB planar framebuffer at `$FA8300` + the boot-time framebuffer setup.** `fb_init(&fb_mode_320x200)` populates `fb_screen` (pointer + width + height + bpp), calls `fb_chunked_init()` (which launches Core 1), builds the demo sprite, clears the planar FB to 0xFF (= palette index 15 = black on default TOS palette), and renders the initial frame. `fb_render_static()` / `fb_render_frame()` are the **legacy template render** (title + ESC hint + a bouncing sprite); they now only paint the initial frame — the per-frame loop is driven by the demo dispatcher (`demo_menu.c`), not `fb_render_frame`. `fb_publish()` (the VBL-synced transpose + cart-FB publish) is the call every demo uses.
- `fb_chunked.c` / `fb_chunked.h` — **chunked off-screen buffer + dual-core publish dispatcher.** `fb_chunked_buffer[320 * 200]` is the byte-per-pixel render target apps draw into. `fb_chunked_init()` launches Core 1 with `fb_core1_loop`, a **generic job dispatcher**: `fb_core1_dispatch(fn, arg)` hands a function+arg to the parked Core 1 over the inter-core FIFO and `fb_core1_wait()` joins — the c2p bottom half and demos' own dual-core work both ride this one path. `fb_chunky_to_planar(planar)` runs c2p into `fb_planar_scratch` (32 KB in RP RAM, natural row-major planar layout) using both cores, then publishes scratch → cart FB via the `fb_chunk_reverse_copy48` Thumb asm worker (chunk-reversed `ldmia/stmia`) so the m68k's predec MOVEM blit lands each 48-byte chunk at its natural image position. The chunk-reversal mapping is specified in `cart_shared.h`.
- `fb_chunked_asm.S` — **hand-written Thumb assembly worker.** `fb_c2p_half(dst, src, src_end)` processes a chunked range using a multiplication-based bit transpose (`((q & 0x01010101) * 0x80402010) >> 28` packs a 4-pixel plane bit into a nibble in one MUL). Writes natural row-major planar output to `dst` — chunk reversal happens in the dispatcher (`fb_chunky_to_planar`), not the worker. Both cores execute this same code on their respective halves. No LUTs in scratch; only two 32-bit constants in registers.
- `fb_font.c` / `fb_font.h` — text primitives. `font_set_font(&font8x8)`, `font_set_color(0)` for palette-index-0 (white on default TOS), `font_move(x, y)`, `font_print(str)`. `render_text` writes single bytes into `fb_chunked_buffer` (no LUT, no plane math) so the cart-bus byte-swap is irrelevant at the font layer.
- `fb_blit.c` / `fb_blit.h` / `fb_blit_asm.S` — bitmap / sprite primitives. `fb_fill_rect(x, y, w, h, color)`, `fb_blit(bm, dst_x, dst_y)` (opaque memcpy per row), `fb_blit_key(bm, dst_x, dst_y, key)` (color-key transparent sprite, inner row in the `fb_blit_key_row` Thumb asm). `_band` variants (`fb_blit_band` / `fb_blit_key_band`) clip vertically to `[y0, y1)` so two cores can render disjoint screen bands. All target the chunked buffer.
- `palette.c` / `palette.h` — RP-driven ST palette: `palette_init()` publishes the template default, `palette_set(entries)` / `palette_set_entry(idx, color)` change it at any time (ST `0RRR0GGG0BBB` words; uint16 writes need no byte-swap).
- `font8x8.h` — 8×8 arcade font (Press Start 2P strike, codes 32..127) + the `FB_FONT font8x8` instance definition. Baseline on row 6; row 7 is the descender row (g q p y j , _). Include from exactly one .c file (currently `fb.c`) to avoid multiple-definition link errors; other files declare `extern const struct FB_FONT font8x8;`.
- **Demo suite** (`demo_menu.c` + `demo_*.c`) — an animated boot menu over four self-contained demos, an input test and two games, each a worked example of "draw into the chunked buffer, publish via `fb_publish`". `demo_menu.c` is the dispatcher (MENU ⇄ ACTIVE state machine; up/down + Return or the number keys launch the highlighted demo, ESC backs out / second ESC exits to GEM, `B` in the menu returns to Booster) and defines the `demo_module_t` interface in `demo.h` (`init` / `render_frame` / `handle_key` / `teardown`) plus the shared `g_show_timing` flag — the hidden `D` key toggles the DRAW/C2P readout in the menu and every demo. The menu is itself a demo: two SidecarTridge logos rotozoomed (INTERP0 texel addressing) with colour-cycling "beating" palettes that dip to black, generated from PNGs by `tools/png_to_texture.py` (`sidecart_logo.h` / `sidecart_text.h`). The demos: `demo_parallax.c` (Uridium-style 3-layer scroll), `demo_3d.c` + `solid3d.h` (flat-shaded geodesic-sphere vector object), `demo_sprites.c` (auto-scaling sprite swarm), `demo_cojorotozoom.c` (full-screen logo rotozoom), and `demo_input.c`: the input test, written against `ikbd.h` only (F1..F4 pick the input mode; a pointer, both buttons, both sticks, the last key and the IKBD counters). They're the reference for the optimization techniques worth copying into new apps: per-file `#pragma GCC optimize("O3")` on hot compute files, `__not_in_flash_func()` on per-frame loops, 8.8 fixed-point with sin/cos LUTs + power-of-two `&`-mask tiling, the SIO **interpolator** in texture-mapping mode (`demo_cojorotozoom.c`), and the **dual-core band split** via `fb_core1_dispatch` + the `_band` blits (`demo_sprites.c`).
- **Games** (`games.h`) — the reference for starting a game, written against the public APIs only: `game_arena.c` (joystick 1 or the cursor keys: grab gems, shoot enemies, three lives) and `game_zap.c` (the mouse: the left button zaps enemies, the right one takes gems, sixty seconds; the HUD lights L and R while they are held). Each has `start` / `key` / `frame`; `demo_games.c` makes them menu entries 6 and 7 (ESC back to the menu, which gets its keyboard mode and its music back: `demo_menu_music()`), and `examples/mini_game` runs one on its own. They share `game_kit.c`: an arena of 16×16 tiles under an 8-pixel HUD, sprites drawn over it and restored under the next frame (`kit_begin_frame()`, so a frame costs a few tile blits per sprite, not the whole arena), labels, a tune and sound effects computed as they play (8-bit PCM through `audio_set_pcm_callback()`, both outputs). Their art is indexed PNGs in `rp/src/assets` sharing one palette, turned into `rp/src/include/art_*.h` by `tools/png_to_bitmap.py` (`convert.sh`). Debug builds of Arena take knobs for measuring the scene: keypad +/- enemies, S their size, F freeze, R / A redraw the arena once / every second.
- `romemul.c` / `romemul.pio` — PIO programs and the runtime that emulates the cartridge ROM/RAM bus to the Atari (driven by `READ_*` / `WRITE_*` GPIOs defined in `include/constants.h`).
- `commemul.c` / `commemul.pio` — **ROM3 cart-bus capture ring; the primary extension point for reading anything the m68k forwards via cart reads in `$FB0000`–`$FBFFFF`.** `commemul_init()` starts a PIO+DMA chain that records every ROM3 read into a 4 KB ring buffer with no CPU/IRQ involvement. The main loop drains it via `commemul_poll(callback)`; each captured 16-bit sample is the cart-bus address that was read (low byte typically carries the payload, high byte the discriminator window — see `ikbd.c` for the canonical example at `$FB8200..$FB82FF`). A reader that falls a whole ring behind is counted (`commemul_getOverruns()`, `commOverruns` over SWD) and resynchronised, and the DMA is re-armed before its transfer count runs out (md-microfirmware-template's version). The upstream `chandler.c` + `tprotocol.h` command-dispatch layer that previously sat on top of commemul was removed — apps that need a multi-byte command channel can wrap `commemul_poll` with their own callback.
- `gconfig.c` / `aconfig.c` — global vs per-app configuration stored in dedicated flash sectors, on top of `settings/` (a key-value store). The global-config defaults in `gconfig.c` mirror the Booster app and include WiFi parameters even though this template no longer brings up networking — **do not trim them**.
- `sdcard.c`, `hw_config.c` — FatFs over SPI/SDIO via the bundled `fatfs-sdk`.
- `select.c`, `reset.c` — SELECT and resets, as in md-microfirmware-template. `select_configure()` runs once, in `main()`: SELECT held at power-on jumps to Booster. While the app runs, `select_poll()` (main loop; never blocks; a GPIO edge interrupt keeps presses made while core 0 is busy) calls the registered callbacks: a short press restarts the RP (`reset_device`), a press held 10 s is a factory reset (`reset_deviceAndEraseFlash`: the global settings are erased, and Booster then clears every app's settings). After an RP restart the ST needs a reset to run the app again. `reset_jump_to_booster()` masks and clears every interrupt before it jumps.
- `st_session.c` / `st_session.h` — the ST's hello at every boot (see "ROM3 signalling windows and ST sessions"): clears the command sentinel, flags a new session for the app, keeps the machine, the TOS version and whether it has a blitter. Also the boot veto (`st_session_veto_boot()` / `st_session_allow_boot()`) and the return to Booster (`st_session_return_to_booster()`).
- `ikbd.c` / `ikbd.h` — the keyboard, the mouse and the joysticks (see the IKBD pipeline): keeps the IKBD samples from the ROM3 ring in order, feeds them to the decoder, writes the input modes' commands (`ikbd_set_input_mode()`, `ikbd_send_commands()`) and sends them again after a hello or an IKBD restart, and gives the app `ikbd_pop_key()`, `ikbd_read_mouse()`, `ikbd_read_joystick()`. ESC press+release within 200 ms signals m68k exit via `CART_CMD_BOOT_GEM`. Keystrokes from host tools enter through `ikbd_inject_byte()`, outside the ST's byte count.
- `ikbd_demux.c` / `ikbd_demux.h` — the decoder: bytes to keys, mouse and sticks, the loss rules, the IKBD's power-up. Plain C, no SDK (`tests/host/test_ikbd_demux.c`).

**Starting a new app:** `examples/hello_text/` is the minimal app with the demos stripped (a drop-in `emul.c` + `CMakeLists.txt`, installed via `apply.sh`, which backs up `rp/` to `rp.bak`); `examples/mini_game/` does the same and boots straight into one of the games, the starting point for a game. The project skill `.claude/skills/framebuffer-app` covers the app-building workflow and APIs in depth.

The `display.c` / `term.c` / `u8g2/` subsystem from upstream `md-microfirmware-template` was deleted — the framebuffer template's UI is just "draw into `fb_screen`".

### Memory layout (`rp/src/memmap_rp.ld`)
The RP2040's 2 MB flash is sliced into named regions, and code is responsible for not stomping on them:

| Region | Origin | Length | Purpose |
| --- | --- | --- | --- |
| `FLASH` | `0x10000000` | 1024 K | App code |
| `ROM_TEMP` | `0x10100000` | 128 K | Scratch area for loaded ROMs |
| `BOOSTER_APP_FLASH` | `0x10120000` | 768 K | Reserved for the Booster app (do not write from this app) |
| `CONFIG_FLASH` | `0x101E0000` | 120 K | 30 sectors of per-app config |
| `GLOBAL_LOOKUP_FLASH` | `0x101FE000` | 4 K | UUID → config-sector lookup |
| `GLOBAL_CONFIG_FLASH` | `0x101FF000` | 4 K | Global config |
| `RAM` | `0x20000000` | 192 K | Normal RAM: data, bss, then the heap up to its end |
| `ROM_IN_RAM` | `0x20030000` | 64 K | The cartridge window (`$FA0000`–`$FAFFFF`), served to the ST by DMA; never heap |

The heap runs from the end of `.bss` to the end of `RAM` and stops before `ROM_IN_RAM` (`__StackLimit` in `memmap_rp.ld`): a heap allowed into the window hands out addresses inside the image the ST executes. `PICO_MALLOC_PANIC=0` (set before `pico_sdk_init()` in `rp/src/CMakeLists.txt`) makes a failed allocation return NULL instead of panicking, so check every allocation; FatFs relies on it to halve its cluster-sized buffer request until it fits. `PICO_HEAP_SIZE` (32 KB) is the heap the link guarantees: static data that leaves less fails with `region RAM overflowed`. Measured: the boot peaks at 13.2 KB (newlib grows the heap in 4 KB steps); with about 9 KB the first settings allocation failed and the app jumped to Booster. The biggest static users are `fb_chunked_buffer` (64 KB), `fb_planar_scratch` (32 KB) and the ROM3 ring (4 KB, aligned to its size).

**Stacks:** core 0's is all of `SCRATCH_Y` and core 1's all of `SCRATCH_X`, 4 KB each (`PICO_STACK_SIZE`, which the SDK also uses for core 1), each with an MPU guard at its bottom (`PICO_USE_STACK_GUARDS`): an overflow is a HardFault, not a silent walk into the other core's stack. Keep big objects off the stack (the `FATFS` object in `emul_start` is static). The deepest static path from `main` is about 1.6 KB plus newlib's printf; core 1's jobs use under 100 bytes.

The build assumes Core 0 owns flash writes (`PICO_FLASH_ASSUME_CORE0_SAFE=1`). The PIO bus emulation runs hot — Core 0 also overclocks to 225 MHz at `VREG_VOLTAGE_1_10`. **Core 1 is owned by `fb_core1_loop`** (`fb_chunked.c`), a parked job dispatcher that runs the c2p bottom half every publish; apps get Core 1 time by handing it work via `fb_core1_dispatch(fn, arg)` / `fb_core1_wait()`, not by launching their own Core 1 entry. Parked, core 1 runs a RAM-only loop (the SDK's inline FIFO calls), so core 0 may erase or program flash while it waits, as the long SELECT press does. That holds only while no job runs: always join a dispatched job (`fb_core1_wait()`) before the main loop goes on, and never write flash while a job runs from flash on core 1.

### App identity
`CURRENT_APP_UUID_KEY` (set from the `APP_UUID_KEY` env var at CMake time, with a placeholder default) is the app's UUID4. It must match the `uuid` field in `desc/app.json` and is used as the key into `GLOBAL_LOOKUP_FLASH` to find this app's config sector. Mismatch → app jumps to Booster.

## Publishing

A successful build leaves three files in `dist/`: `<APP_UUID>-<VERSION>.uf2` (the firmware users install), `<APP_UUID>.json` (the app descriptor) and `rp.uf2.md5sum` (a byproduct; its hash is already inside the descriptor).

The descriptor is generated, not hand-written. Edit `desc/app.json`: fill in `name`, `description`, `image`, `tags`, `devices` and `binary`, and **leave `<APP_UUID>`, `<APP_VERSION>` and `<BINARY_MD5_HASH>` as placeholders** because `build.sh` substitutes them on every run. Write the `binary` URL with those placeholders too, so it tracks the version across releases. `build.sh` aborts if `desc/app.json` is missing.

Getting an app into the public catalogue that Booster downloads is **one pull request** against [`sidecartridge-microfirmwares-store`](https://github.com/sidecartridge/sidecartridge-microfirmwares-store), adding an origin that points at an `apps.json` you host yourself. The store keeps a pointer, not a copy, so later releases need no further pull request. Walkthrough: <https://md-store.sidecartridge.com/build/atari-st/11-get-listed.html>

For an assistant that does not read this file automatically, the same guide publishes a portable copy of the architecture and the hard constraints at <https://md-store.sidecartridge.com/build/atari-st/context.md>. It supplements this file; where the two disagree, this file wins.

## Editing guardrails

- **Never modify** `pico-sdk/`, `pico-extras/`, or `fatfs-sdk/` — they are git submodules pinned to specific upstream revisions, and the build re-pins them on every run. To change FatFs configuration, edit `rp/src/ff/ffconf.h` (project-owned override); the include path is set up so this file wins over the submodule's default.
- Don't touch `main.c` for feature work — start in `emul.c`.
- Match the existing C style (clang-format config in `.clang-format`, clang-tidy in `.clang-tidy` — both wired up via CMake when the binaries are on `PATH`).

## Release workflow

These rules apply to every new version:

- **A version starts with a release branch.** Create `release/vX.Y.Z` from `main`, where `vX.Y.Z`
  is exactly what `version.txt` will contain for that release.
- **One branch per epic, cut from the release branch**, named `epic/NN-<slug>`. All work for the
  epic is committed there, including the `version.txt` bump in the first epic of a release.
- **An epic's pull request targets `release/vX.Y.Z`, never `main`.** It is merged only after
  Diego has verified the epic on real hardware (build, flash, run on an Atari ST).
- **`main` receives the release branch once**, when the whole version is done and verified. Only
  then is the tag pushed (`make tag`), which triggers the release workflow.
- Before tagging: the release build (not a debug build) passes on real hardware, `CHANGELOG.md`
  describes the release for its users, and the planning-reference check above comes back empty.
- Commit, push, open and merge pull requests only when Diego asks.

## Working style

These behavioral guidelines bias toward caution over speed. For trivial tasks, use judgment.

### 1. Think before coding

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them — don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity first

Minimum code that solves the problem. Nothing speculative.
- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical changes

Touch only what you must. Clean up only your own mess.
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it — don't delete it.
- When your changes orphan an import/variable/function, remove it. Don't remove pre-existing dead code unless asked.

The test: every changed line should trace directly to the user's request.

### 4. Goal-driven execution

Define success criteria. Loop until verified.
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan with a verification check per step.

### 5. No AI attribution

Never add AI-tool attribution to commits, PR descriptions, code comments,
docs, or any other artifact. This means **no**:
- "Generated with Claude Code", "Co-authored by Claude", "Made with ChatGPT",
  or any similar phrasing.
- `Co-Authored-By: Claude …`, `Co-Authored-By: ChatGPT …`, or any other
  AI co-author trailer.
- "AI-assisted", "written with the help of an LLM", etc., as comments or
  changelog entries.

Write the message as the human author. Do not mention AI tools used to
produce the work.
